# Architecture and rules

These rules keep the system fast, correct and safe to sell to more shops. Every change should follow them.

## Stack

| Layer                 | Choice                                                                                                                     |
| --------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Backend               | Laravel 13, PHP 8.3+, MySQL 8                                                                                              |
| Admin / back office   | Filament 5 at `/admin` (products, stock, reports, users, settings)                                                         |
| POS checkout screen   | Vue 3 + Inertia (starter kit), later a PWA with IndexedDB for offline mode                                                 |
| Auth                  | Fortify (starter kit) for the till and `/admin`: login throttling, 2FA (required for the owner in production), passkeys    |
| Roles & permissions   | spatie/laravel-permission, defined in `config/pos.php`                                                                     |
| Optional modules      | Laravel Pennant feature flags, per shop                                                                                    |
| Cache / queues (prod) | The database (cache, sessions, queue); Redis optional                                                                      |
| Hosting               | A cloud VPS per [docs/deploy/CLOUD.md](deploy/CLOUD.md): Caddy, PHP-FPM, MySQL 8.4, one user, database and pool per client |
| Report exports        | openspout (Excel), dompdf (PDF), a print page for the browser                                                              |

## The ten rules

1. **Stock changes only through `StockService`.** Never update `stock_levels` or `stock_batches` directly. Every change is a `stock_movements` row, created in a transaction with a row lock on the item's stock level. A batch-tracked item (`products.track_batches`, every medicine) moves only through `issue()` / `receive()` / `restore()` (first expiry first out, one movement per batch; a write-off is `writeOff()`, an issue of the named batch at its own cost); `record()` refuses it. Purchasing goes through the same methods (a posted GRN is a `stock_in` through `receive()` or `record()`), plus `reverseReceipt()` for a reversing GRN and `returnToSupplier()` for a supplier return.
2. **Money is an integer in minor units** (LKR 1,250.50 = `125050`). Use `App\Support\Money`. Never use floats for money. The one exception (PHARMACY.md Q9): costs per base unit (average and last cost on `stock_levels`, a batch's purchase cost, the ledger's `received_cost`) are DECIMAL(20,4) minor units, held as strings and calculated with `App\Support\UnitCost` (bcmath); anything shown or added up is rounded back to whole minor units.
3. **Quantities are DECIMAL(14,3)** (selling oil by the litre, cable by the metre). Pass them through `Quantity::normalize()`. **Stock is always in the variant's base unit**; a pack (strip, box, drum) converts by its factor before it reaches `StockService` (`VariantUnit::toBase()`). A product with `whole_units_only` (medicines) takes whole numbers of the unit used: 1 strip or 3 tablets, never 0.5 box.
4. **Prices come from the server's price list, never from the client.** Tills send variant ids, units and quantities only. Every sellable unit has its own price; none is derived from another unit's. **One exception, the typed price** (PHARMACY.md §4.3): a product with `allow_price_override` that does not track stock (a service such as the consultation fee) may be sold at a price the till sends (`lines.*.price`), only by a user with `pos.price_override`, only above zero; the line keeps the price list's price as `list_price` and each one is audited (`price_overridden`). Anything else that sends a price is refused. An OPD bill's medicine lines are not priced by the client either: the server spreads the typed Medicines amount over them by its own list prices (an unpriced line by its cost); only an offline sale's replay weighs them by the prices the till sent, so it records what the till charged. A medicine line's share is never sent to a till (it could give a cost away).
5. **Every tenant table has `shop_id` and uses `BelongsToShop`.** Never accept `shop_id` from input. With no current shop, tenant queries return nothing, so commands and jobs must call `app(CurrentShop::class)->set($shop)` or `runAs()`. Child tables without `shop_id` (sale items, payments, variant prices, attribute values, audit logs) are **only ever reached through their parent** (`$sale->items`), never with `find($idFromRequest)`.
6. **Sales, stock movements and audit logs are never edited or deleted.** Use void, return or adjustment instead. Two exceptions, both commands: `pos:go-live-reset` removes the rehearsal's transactions before go-live (stock through `StockService::forgetMovements()`), and `pos:audit-prune` deletes audit entries past the shop's retention (cost revaluations are kept).
7. **Check permissions in services**, not only by hiding buttons: `$user->can('sales.void')`. The audit log holds cost-price history, so its screen requires `audit.view` (Owner only).
8. **Snapshot what can change.** Sale items copy the name, SKU, price and cost (the weighted average at that moment) at the time of sale, the unit sold with its factor and base quantity, the tax category the line was taxed under, and (batch-tracked items) each batch's number and expiry as sold (`sale_item_batches`).
9. **New features for some shops go behind a module flag.** Add the module to `config/pos.php` and protect its routes with `->middleware('module:key')`. Read it with `$shop->hasModule('key')`; change it only through `ModuleService` (it applies `pos.module_requires`). Never read `POS_PROFILE` at runtime.
10. **Every service change comes with a test** in `tests/Feature/Pos`.

## How the main flows work

**Checkout** (`CheckoutService::checkout`):
validate till and cashier → resolve each line's location (omitted = the till's; it must be active and sellable, and the cashier must be allowed there: users' allowed locations, `location_user`; with `multi_location`, none = the shop's default location only, or every location with `locations.all` (the owner); without it, none = every location) → load variants, their units and server prices → check typed prices (rule 4's one exception) and, on an OPD bill, the till, `pos.opd_bill`, no discounts and the Medicines amount → resolve each line's unit (omitted = base unit; it must be sellable **at the line's location**, `canSellUnitAt()`) and its base quantity → calculate lines, discounts (spread across lines), tax (inclusive or exclusive; only on `standard` products, `exempt` lines carry none); on an OPD bill the medicine lines (stock items) are not priced one by one: the typed Medicines amount is spread over them (`Money::allocate`, remainder to the largest), so their totals add up to the amount. Online the weight is the list gross, else the cost (unit cost × quantity), else every line 1; an offline replay weighs by the prices the till sent (it has no cost). Per-line OPD shares are never sent to the till: the quote's medicine lines have null `line_total`, `tax_amount` and `sale_discount_share` with `medicines_total` / `medicines_tax` on the totals, and the receipt's medicine items have no amounts (two narrow exceptions: a refund of one medicine line shows on a reprint, and with shop tax on, per-line tax rounding of the Medicines figures depends on the split; see [PHARMACY.md, as built (branch 8)](PHARMACY.md#as-built-branch-8)) → enforce the cashier discount limit → check prescription lines (a prescriber when the shop requires one; the patient's name for a controlled drug with the register on) → validate payments (change from cash only; a bank transfer reference when the shop requires one) → on an OPD bill, note its medicines' list value (Σ list price × quantity of the priced ones, never a cost) and whether the Medicines amount was below the shop's warning share of it (`opd_below_list_warning_percent`; the till warns, never blocks; `sales.opd_medicines_list_value`, `opd_below_list`) → in one transaction, reserve the invoice number (`T1-000001`), save the sale, items and payments, and record `sale` stock movements of each line's base quantity at the line's location (`sale_items.location_id`). A batch-tracked line is allocated first expiry first out under the stock level's lock (never an expired batch, nor one inside the minimum days to expiry), one movement and one `sale_item_batches` row per batch; a pharmacist may pick the batch (`pos.batch_override`). Every line snapshots the medicine's schedule, prescriber and Rx reference. `CheckoutService::quote()` runs the same maths without saving; given the till, it also previews each batch line's batches and shortfall (`BatchPlanner`, read only; a batch pick checkout would refuse is refused there too, with the same message) ([PHARMACY.md, as built (branch 8)](PHARMACY.md#as-built-branch-8)).
If the till retries with the same `uuid`, it gets back the original sale, so a sale is never recorded twice.

**Offline sync:** the till creates the sale with its own UUID and invoice number, then sends it with `isOfflineSync: true`. The server accepts it even if stock would go negative, because the sale already happened, and stamps `synced_at`. For batch-tracked items it keeps the till's proposed batches where still valid, re-allocates the rest, and books what the batches can't cover to the item's **unallocated batch** (which raises an alert and is settled by the next receipt); every difference is a review reason, never a rejection ([PHARMACY.md §6, as built](PHARMACY.md#as-built-branch-5)). The same holds for the checkout rules: a location the cashier may not use, a unit not sold there, a missing prescriber, a typed price not allowed, an OPD bill's problems, a missing bank transfer reference are recorded and flagged. Each upload carries the till's clock (`device_time`); the server stores the difference from its own (`sales.clock_offset_seconds`), and a till out by more than the shop's tolerance (`till_clock_tolerance_minutes`) is flagged `clock`, not rejected. Reports and the dashboard count a sale at `sales.reported_at`: its `sold_at`, or the server's time when the till's clock was out, when the corrected time is after the sale reached the server, or when the till's time is outside what a TIMESTAMP column holds (then `sold_at` is the arrival time too) ([PHARMACY.md §7.5](PHARMACY.md#75-till-clock-and-disabled-cashiers-decided-2026-10-20)).

**Returns:** refunds are proportional to what was actually paid for each line (after discounts; an OPD medicine line: its share of the Medicines amount), by base units, so 10 tablets back from a box of 30 refund a third of it. Each line of a return is entered in the sold unit or in base units and has its own "Put back into stock?" (off by default for fridge items, controlled drugs and faulty goods); limits are what was sold less what already came back. Returning the last units refunds the exact remainder, so rounding never drifts. Stock goes back to the line's location unless the line is not restocked; voids too. A batch-tracked line goes back into the exact batches it took (returns: latest expiry first unless the user says which). The refund is paid back by cash, card or bank transfer, with its reference (`ReturnService::processLines()`).

**Receipts** (`ReceiptService`): every printed receipt (first print, reprint, refund slip, void slip, A4 invoice) is built from the sale's own rows (lines with their description, strength, units, prices, batch and expiry snapshots; payments; returns), never from the product as it is now, so a reprint prints what was sold; reprints are logged (`receipt.reprinted`) and marked. A pharmacy prints the thermal layout: `Receipts/ReceiptLayout` lays a receipt out as fixed-width lines (48 characters on 80 mm paper, 32 on 58 mm), the browser prints those lines in a monospaced font at the paper's width, and `Receipts/EscPos` turns the same lines into ESC/POS bytes. What the layout prints under each medicine (batch, expiry, prescriber), the paper width and the OPD bill's medicines are shop settings (Receipt settings), read when printing. Offline receipts are laid out by the till with `resources/js/lib/receipt/layout.ts`, a mirror of `ReceiptLayout::sale()`: change both together (`ReceiptLayoutParityTest` runs the till's code under node and compares). A retail shop's sale receipt is the HTML receipt it always was ([PHARMACY.md, as built (branch 9)](PHARMACY.md#as-built-branch-9)).

**Shifts:** expected cash = opening float + cash taken − change given − cash refunds. Closing records the counted cash and the difference. The cashier sees their own shift's summary (bills, sales, refunds, voids, payments by method, the drawer) when closing it, and may print it (`ShiftService::summary()`).

**Reports** (`ReportService`, Reports menu, `reports.view`; [PHARMACY.md, as built (branch 11)](PHARMACY.md#as-built-branch-11)): every figure is an SQL aggregate over the shop's days with date presets; a sale counts at `sales.reported_at`, a refund on the day it was given, a voided bill not at all. With `multi_location`, figures about bills filter by the counter (`sales.location_id`) and figures about what was sold by the stock pool (`sale_items.location_id`). Reports of several tables read the sale lines once (`lineFacts()`) and group them in PHP. Profit reads revenue and **cost from the sale lines** (an OPD medicine line: its stored share; cost as stored when sold, so no per-tablet rounding; restocked returns take back their line's cost); stock values read the ledger and each location's weighted average. Every report exports to CSV, Excel and PDF and has a print page, all with the columns and totals on screen (`ReportExporter`).

**Dashboard** (`/admin`, `reports.view`): number tiles first (today, the counters, stock control, payables), then charts, then the best sellers and low stock tables. Every figure is a `ReportService` method, so a tile or chart always equals its report. The charts (Filament chart widgets, `Widgets/Concerns/DashboardChart`) are net sales by counter, consultation fees against medicines (pharmacy), the top 10 items by net sales, payment methods and stock value at cost (`cost.view`; by location with `multi_location`, else by category). Each has the reports' date presets as its filter, refreshes every minute and reuses its figures for a minute (cache per shop, chart and period). A counter has one colour on every chart (`Filament/Support/ChartColors`, checked for colour-blind readers in both modes); the brand and status colours are never used for data. Gross profit today shows revenue − cost and the margin under the figure, red below zero, and the OPD bills' medicines when their typed amount was below cost. **A clinic's dashboard** (pharmacy module) is its own layout on a 12-column grid (`Dashboard::content()`, widgets in `Filament/Widgets/Clinic`, figures from `ClinicDashboardService`, which reads the same `ReportService` and `ExpiryService` methods and keeps each part a minute per shop and day): greeting, today's insights (plain rules), KPI cards (the only polling widget), location performance, this week's trend, stock value (`cost.view`), stock alerts (`stock.view`), today's OPD bills and activity, then the widgets that show only when something needs action ([PHARMACY.md, as built (branch 11c)](PHARMACY.md#as-built-branch-11c)).

**Branding** (Shop settings → Branding, `settings.manage`): the logo (`shops.logo_path`, also on Receipt settings and printed on receipts), the favicon and the brand colour (`brand_color` and `favicon_path` shop settings). `BrandPalette` turns the colour into shades 50–950 (the colour itself at the shade nearest its lightness) and moves a shade only when text on it would fall below WCAG AA (4.5:1): shade 50 on 600 (buttons, both modes), 400 on the dark surface, 950 on 400 (the till's dark button). The admin panel's `primary` becomes that scale (registered when the page renders, so the user's shop is known); danger, warning and success never change. The till's `--primary`, `--primary-foreground` and `--ring` are set in `app.blade.php` (600 / 50 light, 400 / 950 dark), with the favicon and `theme-color`. "Suggest from logo" picks the logo's dominant colour on the server with GD. No colour set: the theme's colours (classic: the panel's amber and the till's own colours, as before).

**Colour theme** (Settings → Appearance, the owner only): a preset from `App\Support\ThemePresets` (`theme_preset` shop setting): `classic` (the look from before, nothing printed), `clinic_teal`, `ocean_blue`, `plum`, `slate`. Unset: Clinic Teal for a pharmacy shop, classic for any other. `ThemeService` puts `data-pos-theme` on `<html>` and the preset's variables in `<head>` of the till and settings pages (app.css's names, before the brand colour's block, which still overrides primary) and of the admin panel (`HEAD_START` render hook; `--pos-*` variables read by the Filament Vite theme `resources/css/filament/admin/theme.css`, scoped to `html[data-pos-theme]`), and registers the preset's primary, success, danger and warning palettes. Saving a preset clears the brand colour. Every text colour of every preset passes WCAG AA in both modes, and the sidebar's icons, focus ring and active bar 3:1 (`Unit/ThemePresetsTest`); the sidebar's hover, active and accent tokens are worked out from each preset's sidebar and primary colours.

**Goods received** (`purchasing`, `GoodsReceiptService`): a GRN is drafted (no stock moves), then posted in one transaction: numbered (`GRN-000001`), each line brought in as a `stock_in` in base units (a box of 100 is 100 tablets) at the GRN's location, into its batch for batch-tracked items (which settles any unallocated stock first), at its effective cost per base unit `line total ÷ ((paid + free) × factor)`, the invoice discount spread over the lines by value; tax (VAT) on the invoice is part of the cost, entered per line or once for the invoice (spread by value after discounts, never both); the paid quantity counts against the purchase order, if any. New orders and GRNs start at the user's location, or at the default location when the shop receives centrally (`receive_at_default_location`). Posted GRNs never change: a mistake is put right by a reversing GRN, which takes the same quantities out of the same batches at the same costs. Supplier returns leave named batches at their purchase cost. An item missing from the catalog can be created from an order or GRN line (`ReceivingItemService`: a barcode in use is refused, a likely duplicate is a warning); created by someone without `products.manage`, it is `needs_review`: received, but left out of the till's search, the offline catalog and checkout until reviewed. A supplier's balance is its go-live opening balance + posted GRNs − returns − payments; opening balances and payments, like GRNs, are corrected only by reversing entries ([PHARMACY.md §4.9, as built](PHARMACY.md#as-built-branch-6)).

**Supplier payables** (`purchasing`, `SupplierPayablesService`): each posted GRN and opening entry is an invoice owed, due on its invoice date (else the date received) + the supplier's terms; each payment, return and opening credit is a credit. Credits are allocated to invoices (a payment oldest due first unless the user picks; a return to the GRN its batches came from), insert-only, undone by reversing rows; what is not allocated is the supplier's credit. Reversing a payment, GRN or opening entry undoes its allocations. Everything that changes allocations locks the supplier row first. The balance always equals the invoices outstanding less the credit (`SupplierService::reconcile()`) ([PHARMACY.md, as built (branch 6b)](PHARMACY.md#as-built-branch-6b)).

**Tax category.** `products.tax_category` is `standard` (the shop's rate applies) or `exempt` (no tax). Every product existing before it is standard, so retail tax is unchanged; new medicines default to exempt ([PHARMACY.md §4.1](PHARMACY.md#as-built-branch-3)). The offline mirror `resources/js/lib/offline/pricing.ts` applies the same rule.

**Units.** Every variant has one base unit (`variant_units.is_base`, named after `products.unit`, factor 1) and optionally packs, each with its own factor, barcode and price (`variant_prices.variant_unit_id`). `ProductVariant::prices()` returns base-unit prices only, which is what every screen built before units reads. The base unit can't change once the product has a stock movement. Selling rules (Q16) are in `ProductVariant::canSellUnit()`; selling loose can differ per location (`variant_unit_locations`, `canSellUnitAt()`, read by checkout and the till since PHARMACY.md branch 8); the till offers each item's units sold at its location, and a pack's barcode scans to that pack; details in [PHARMACY.md §4.2](PHARMACY.md#as-built-branch-2).

**Imports** (`ImportService`, `imports.manage`, Administration → Imports): items, suppliers, opening stock and supplier opening invoices from .xlsx or .csv, on downloadable templates or the shop's own layout. Upload → match the columns (saved per shop) → check (the dry run: errors, warnings, create / update / skip per row, an error report; nothing written) → confirm → `RunImport` on the queue checks again and writes the whole file in one transaction through the services (`ProductCatalogService`, `StockService` opening movements per batch, `SupplierService` opening invoices), or nothing. Rows already on file are skipped or updated, never created twice ([PHARMACY.md §10, as built](PHARMACY.md#as-built-branch-7)).

**Stock control** (docs/PHARMACY.md, [as built (branch 10)](PHARMACY.md#as-built-branch-10)): the Expiry lists (pharmacy) show the batches holding stock that have expired (expiry date before today) or expire within `near_expiry_warning_days`, per location, valued at batch cost, never the unallocated batch; `pos:expiry-digest` sends the owner a daily digest (**needs the scheduler**). Selected batches are written off (`StockWriteOffService`, `stock.write_off`: one note per location, `adjustment_out` at batch cost, audited), moved to a location that does not sell (a transfer) or returned to the supplier. Stock requests (`multi_location`, `stock.request`; the OPD's cashier from the till) are fulfilled by `stock.transfer` with transfers that name them, in parts, first expiry first out. Reorder suggestions top a location up to its par level (`stock_levels.par_level`; else twice the reorder level) less what is coming and expired stock, as a stock request or as draft purchase orders per item's last supplier in its last pack. Stock counts are documents (`stock.count`; posting needs `stock.adjust`): each line keeps a snapshot of what the system held when it was counted, and posting writes counted − snapshot as count corrections in one transaction (`StockService::adjustBy()` / `adjustBatchBy()`), so a count never blocks sales and what sells or moves between counting and posting is not a variance.

**Labels** (`labels`, `LabelService`, docs/PHARMACY.md, [as built (branch 7b)](PHARMACY.md#as-built-branch-7b)): every item has a barcode (in-store EAN-13 `200` + its id when it has no manufacturer's); a pack without one gets `201` + its id when its labels first print, or in bulk from the product list, never replacing a barcode it has (`BarcodeService`, unique across items and packs). Labels are asked for from a product, a delivery, batches or the product list, printed at once or collected in the user's print queue, and logged (`label_prints`). `LabelLayout` fits them on the template's label: bars in whole printer dots, never narrower than 0.25 mm, text never under 6 pt (shrink, then wrap the name, then cut it short), and a template that can't fit its samples is not saved. The print is a browser page whose every page is exactly one label or one sheet (`@page`), so any label printer's driver prints it; raw TSPL / ZPL is left for the deployment.

**Costing: weighted average cost (WAC), per variant per location.** `stock_levels.average_cost` is the average cost of a base unit of the stock on hand at that location, DECIMAL(20,4) minor units; `stock_levels.last_cost` is what the latest receipt there cost. `product_variants.cost_price` is kept as the blend across locations (Σ on hand × average ÷ Σ on hand, whole minor units) and `last_cost_price` as the latest receipt anywhere, so a one-location shop sees exactly one average, as before.

- A receipt with a unit cost (Opening, Stock In, later goods received) re-averages the cost at its location in `StockService::record`, inside the stock transaction, with the variant row and that stock level locked:
  `new average = (on hand × average + qty × unit cost) ÷ (on hand + qty)`, exact and rounded half up to 4 places (`UnitCost::weightedAverage()`).
  If on hand there is zero or below, the new average is simply the unit cost.
  Example: 10 on hand at 950 plus 10 received at 1,100 gives (9,500 + 11,000) ÷ 20 = **1,025**.
- A **transfer** (`StockService::transfer()`, `multi_location`) leaves at the source location's average and re-averages the destination with it; the item's blend does not change. Transfers never take a location below zero.
- A posted goods received note re-averages at each line's effective cost (free goods and discounts included, 4 places). A **reversing GRN** takes its cost back out exactly: `new average = (on hand × average − qty × unit cost) ÷ (on hand − qty)` (`UnitCost::withoutReceipt()`; nothing left: the average stands), so reversing an untouched receipt restores the average it replaced.
- Stock In without a unit cost, returns, voids, adjustments, write-offs, sales and supplier returns never change an average. A supplier return's ledger cost is the batch's purchase cost (what the credit is worked out at), and so is a write-off's. Returns and voids put stock back at the original sale line's `unit_cost` per base unit (`unit_cost ÷ unit_factor`), at the line's location.
- Sale lines snapshot `unit_cost` at the time of sale (rule 8), per sold unit, from the line's location (a box costs its factor × that location's base average, rounded to minor units). The ledger's `stock_movements.unit_cost` stays whole minor units. Profit reports use each line's own `unit_cost`, so they keep the cost the item had when it was sold, however the average moves later, without the ledger's rounding per base unit.
- A location that never held an item starts at the item's blended cost. Lock order: variant rows (receipts, transfers, revaluations) by id, then stock levels by (location, variant).
- Every change of the blended cost is audited (the variant is an audited model). The product form shows the blend and last cost read-only; only **Revalue cost** (`cost.manage`, owner by default) sets an average by hand, per location, with a required reason that is written to the audit log as a `cost_revalued` entry.
- `pos:stock-rebuild --costs` replays every location's average and last cost from the ledger (receipts and transfers by the exact `received_cost` they carried, receipt reversals taking theirs back out, revaluations from the audit log) and reports differences; `--fix` writes them, audited.
- Stock values (Stock levels, Stock valuation, dashboard) use max(on hand, 0) × that location's average per item per location: stock below zero is a count to fix, not a negative value. Low stock is per location too, with an optional per-location reorder level ([PHARMACY.md §5, as built](PHARMACY.md#as-built-branch-4)) and par level (branch 10). Expiry lists and write-offs value a batch at its own purchase cost; count variances at the location's average.

## Install profiles

`POS_PROFILE` (`retail` | `pharmacy`, default `retail`) picks a profile from `config('pos.profiles')`. A profile is **install-time defaults only**: which seeders `db:seed` runs (reference data, demo shop), and what `pos:install` creates for a new shop (business type, locations, roles, the modules it starts with, and the shop settings it starts with over `pos.shop_defaults`: the pharmacy profile's short-expiry window is 90 days, it receives goods at the default location, cashiers may give no discount, prescription lines need the prescriber and a bank transfer needs its reference). After that, module state lives only in Pennant per shop; changing `POS_PROFILE` on a running install changes nothing.

```bash
php artisan pos:install --profile=pharmacy   # GEN + DOC, QUAR (does not sell), pharmacy modules on
php artisan migrate:fresh --seed             # seeds the POS_PROFILE profile's demo shop
```

The test suite is pinned to `retail` in `phpunit.xml`; pharmacy tests extend `PharmacyTestCase`.

## Multi-client plan

- **Now:** one codebase, one deployment and database per client, on cloud VPSs that several clients may share (one Linux user, PHP pool and database user each; [docs/deploy/CLOUD.md](deploy/CLOUD.md)). This is the strongest isolation, and each client is onboarded with `scripts/add-client.sh`, which runs `php artisan pos:install`.
